# Counterhand MCP for WooCommerce — coding rules

## Architecture
- **DDD feature modules**: each feature under `src/Features/<Name>/` owns its views, admin glue and services. Domain objects live in `<Feature>/Domain/`. Cross-feature dependencies go through interfaces (e.g. `TokenRepositoryInterface`), never concrete classes of another feature.
- **Placement rule — the owning feature publishes its contract.** `Shared/` is only for things with no natural owner (`FeatureInterface`, `JsonRpc/`, `Exception/`, `Tool/`). An interface belongs next to the feature that defines it, even when six others import it: `ApiScope` and `TokenRepositoryInterface` live in `Features/Tokens/Domain/`, `ProviderInterface` in `Features/Playground/Provider/`, `RestGatewayInterface` in `Features/WooCommerceTools/Infrastructure/`. Before adding to `Shared/`, count the consumers — **one consumer means it belongs in the slice**. `src/Shared/Tool/` is three contract files and must stay that way; nothing WooCommerce-specific goes in `src/Shared/`.
- **SOLID**: no `instanceof` branching on concrete types in feature/application code — put the varying behaviour on the interface. One responsibility per class; extract a service when a feature class grows a second workflow.
- **Value objects over arrays**: structured data crossing a boundary (return values, transients, JSON payloads, view data) is a `final readonly` VO or a backed enum, not an `array{...}` shape. `to_array()` only at the serialization edge (`wp_send_json_*`, transients).
- **DRY**: compute once, pass down — views receive data, they don't re-fetch it.

## Protocol boundaries
- **The MCP wire format belongs to one slice.** Only `Features/McpServer` may build or parse JSON-RPC envelopes and MCP result shapes (`content`, `isError`, `structuredContent`, error codes). Business logic elsewhere consumes `ToolInterface` / `ToolRegistry` directly — the way `AgentLoop::tool_definitions()` already does — never the wire format.
- **In-process tool calls go through the seam, never an envelope.** `ToolDispatcherInterface::dispatch()` is the transport-neutral pipeline (defaults → validation → scope gate → execute → `counterhand_tool_called`) and returns a `DispatchOutcome`; the JSON-RPC handler and `AgentLoop` both consume it. A new in-process caller uses it too. Anything that changes what a call *does* (dry-run, undo snapshots) belongs inside it, so every transport gets it at once. The only envelope outside McpServer is `ConnectReadiness`'s `initialize` probe, which is a real HTTP request to the store.
- **One tool pipeline.** Schema-default application, argument validation, scope enforcement and the audit hook run in exactly one place. If a caller can reach `ToolInterface::execute()` without passing through that pipeline, that is a bug, not a shortcut.
- **The `/mcp` path is declared once.** It currently appears in four places (`McpServerFeature`, `CanonicalUri`, `ConnectReadiness`, `SettingsFeature`); do not add a fifth — route any new consumer through `CanonicalUri`.
- **Features expose UI to Settings through a contract.** `render_tab()` is an informal convention with no interface behind it, and `SettingsFeature` already injects three concrete siblings for it. Don't add a fourth concrete — introduce/extend a tab contract instead.

## Tool-surface size
- **Never cap the surface when the provider can defer it.** Selection accuracy falls off past roughly 30–50 *eagerly loaded* tools — that is the real constraint, not any wire limit. Anthropic's answer is the tool search tool: send every definition, mark the tail `defer_loading: true`, and Claude searches names/descriptions/argument names on demand. Deferred definitions stay out of the system-prompt prefix, so they cost nothing until surfaced and the prompt cache survives. Keep 3–5 tools eager (the API rejects a request with everything deferred) and never defer the search tool itself.
- **The ceiling is provider knowledge, not loop knowledge.** `ProviderInterface::max_eager_tools()` returns null when the provider can search a catalogue and a number when it cannot; `with_tool_search()` decides how a catalogue is spelled. `AgentLoop` asks — it must never hardcode a limit or branch on a provider. OpenAI and Gemini both hard-reject more than 128 tools and have no deferred-loading equivalent, so their adapters return a real number.
- **A refusal is the last resort, and must say what to do.** Only a provider with no deferred loading refuses, and the message names the count, the ceiling, how many to untick, and that an Anthropic model removes the limit.

## The official WordPress MCP stack (state as of July 2026)
Know the landscape before building or duplicating anything:
- **Abilities API is WordPress core since 6.9** (`wp_register_ability` on `wp_abilities_api_init`, JSON-schema in/out, `permission_callback`). **WooCommerce ≥10.3 ships its own experimental MCP server** (feature-flagged, developer preview): through 11.2 it exposes hand-authored product/order abilities via the bundled `wordpress/mcp-adapter`, authenticated with REST API keys (`X-MCP-API-Key`). From 11.3 the server, flag and bundled adapter are gone: abilities are always registered, and the standalone adapter plugin exposes them with application passwords.
- **This plugin's reason to exist is the gaps**: OAuth 2.1 for self-hosted HTTP transport (core has none — WordPress.com only), breadth beyond products/orders (coupons, customers, reports, settings, shipping, tax, wp/v2), scoped tokens with per-client consent, confirmation-gated risky writes, and the chat playground. Don't reimplement what core now does well; don't drop what core still lacks.
- **Runtime derivation from wc/v3 is validated, keep it.** WooCommerce's own 10.3 `AbilitiesRestBridge` used the same pattern (derive schema + permissions from live REST controllers). Core later hand-authored its 7 canonical abilities for its *public contract* — that is curation, not a repudiation of derivation; our `FieldProfile` pruning plays the same role.
- **Never register anything under the `woocommerce/` ability prefix** — reserved for core (10.9 announcement). If we ever bridge our tools into the Abilities API for interop with the official adapter, use our own prefix and treat it as a thin adapter over `ToolInterface`, not a second tool implementation.
- **Do not vendor `wordpress/mcp-adapter`.** It is pre-1.0 (breaking changes at 0.3.0, 0.6.0 and 0.7.0), WP ≥6.9 only, and recommends Jetpack Autoloader — all three collide with the zero-runtime-dependency rule. The in-house `Shared/JsonRpc` layer stays.

### Abilities, as registered on a real store (verified October 2026, WP 7.1.3)
Read `wp-includes/abilities-api.php` and `abilities-api/class-wp-ability.php` in the e2e store, not blog posts; dump what plugins actually register with `wp eval-file` (the inventory script pattern: name, category, meta, schema types, `check_permissions` per user).
- **Exposure flags.** Core 7.1 defines `meta.public` ("meant for clients such as REST, MCP or AI agents"; seeds `show_in_rest`). Plugins mostly set `meta.mcp.public` instead: WooCommerce 11.2's seven `woocommerce/*` abilities have `public=false, mcp.public=true`, as do Yoast's and WPForms'. `meta.mcp.public` decides when set and `meta.public` is the fallback, the official adapter's rule; a malformed `meta.mcp` fails closed and `mcp.type` of `resource` or `prompt` is not a tool. Core's own three (`core/get-site-info`, `get-user-info`, `get-environment-info`) are `public=true`.
- **What plugins ship.** Yoast 28.8: eleven `yoast-seo/*` by default. The post SEO data and score abilities register only in production mode (`yoast_seo_development_mode` forces it in a test store) and with their analysis setting on, inclusive-language scores off by default. Seven site-wide writes (sitemaps, schema, social tags, site representation) are new in 28.8, not production-gated, and each `set-*` can switch a feature off. Its `*_rendered` output expands `%%cf_...%%` with no check for protected keys. WPForms Lite 2.0.3: eight `wpforms/*`, three exposed by default and all eight with its "write access" toggle on, `describe-editing-schema` following the toggle though it is a read. Pro adds `get-entry`, `get-entry-summaries` and `search-entries`, with visitors' data (from its docs; no Pro source read). `get-form-stats` declares a boolean `required` on a property, which is invalid JSON Schema. Rank Math 1.0.280 (free): registers **nothing** while its product registration is invalid, as on a fresh store (`Helper::is_invalid_registration()` stops it before `init_abilities`; the `rank_math_registration_skip` option passes that in a test store). Set up, it registers 29 `rank-math/*`, all `mcp.public`, with every write declared `destructive: false`, including `set-global-seo-settings` and `fix-site-seo`. Its adapter's three `mcp-adapter/*` meta-tools must be skipped (they would let a client call any ability, bypassing our gate). **It also starts two MCP servers of its own, whatever its registration state**, under `/wp-json/mcp/`: an application password with the right capability reaches every `mcp.public` ability there, including WooCommerce's, past all our scopes and confirmations. We warn in Settings and do not disable another plugin's server. Its `get-settings` returned `facebook_secret`, `get-system-status` private database details, `get-seo-scores` coupon codes and `analyze-post-content` private post bodies, all in `AbilityCatalog::SKIPPED_ABILITIES`. ACF 6.8: behind `acf/settings/enable_acf_ai` (off by default), six `acf/*` for field groups, post types and taxonomies, plus list, create, view, update and delete abilities per post type or taxonomy with its own "Allow AI Access" on, so the set grows with the site. All `mcp.public`.
- **Annotations are `readonly` / `destructive` / `idempotent`, each `true`, `false` or `null`.** Yoast's update sets `destructive: null` ("we can't claim this is truly non-destructive"). Map `null` the way MCP's defaults do: not read-only, destructive, not idempotent.
- **`WP_Ability::execute()` is the whole pipeline**: input normalization and validation, the ability's own `permission_callback` against the current user, the callback, output validation, and since 7.1 the `wp_ability_invoked` / `wp_pre_execute_ability` hooks. Never call the callbacks directly.
- **Do not probe permission at list time for item-level abilities.** `check_permissions()` without input fails for anything that needs an id (`wpforms/get-form` answers forbidden with no form), the same trap as probing `/products/{id}`. Execution checks permission with the real input anyway.
- **Schemas are not always objects.** `input_schema` may be a scalar or absent; an MCP `inputSchema` must be an object, so a bridge wraps it.

### The Abilities bridge (`Features/Abilities`)
- **One integration per plugin.** An exposed ability becomes a tool in an `IntegrationGroup` keyed by its namespace, with scopes `integration:<namespace>:read|write`. Each ships off, with its own toggle and consent row, and a grant for one plugin never reaches another. Scope grammar lives in `Tokens/Domain`; a token row parses without asking which plugins are active.
- **Code that handles any group or scope takes `ScopeGroupInterface` / `ScopeInterface`, and reads `key()`.** `ToolGroup::cases()` and `ApiScope::cases()` are only the shipped half; `ScopeGroups::all()` is the whole set. A new source of groups publishes through the `counterhand_integration_groups` filter, so a shipped integration takes the path a third party would.
- **Never bridge `woocommerce/*`, `core/*` or `mcp-adapter/*`.** All `woocommerce/*` duplicate generated tools, so an integration grant would reach products and orders past those groups' scopes. Core is no plugin, and its reports would add a separate grant for environment data. `contact-form-7/*`, `flamingo/*` and `acf/*` are served by our own tools, whose policies abilities would bypass: ACF's return password fields, and registering a field group with a field named `_price` would let our tools write that meta. `mcp-adapter/execute-ability` would bypass every gate.
- **Every bridged write needs confirmation, whatever it declares.** A plugin's label about itself does not decide whether a person gets asked: Rank Math marks its settings writes `destructive: false`. `AbilityTool::requires_confirmation()` is simply not read-only. A tool only declares that: `ToolDispatcher` publishes `confirm` (`published_schema()`), enforces it and strips it before `execute()`, for every kind of tool and transport.
- **A grant holds what was on the screen.** `ToolRegistry::integration_tools_by_scope()` gives the consent screen the integration tools a scope reaches, the form carries that list back, the token stores it intersected with what is served at approval (`approved_tools`), and `passes_gates` refuses anything else. A plugin update that adds an ability therefore adds nothing to existing connections until someone connects again; Yoast 28.8 added seven site-wide writes this way. A stored token is always pinned; only the admin's own chat has none.
- **A plugin's reach is stated in its own consent wording** (`KnownPluginCopy`). Yoast and Rank Math read drafts of products and pages through `edit_post`, past the products and content scopes, and that is accepted because the wording says so and the owner could edit them anyway. An ability that returns secrets or reaches another scope's data is skipped by name; its arguments can be held to an `ArgumentPolicy` (`AbilityCatalog::policy_of`).
- **A template field reads more than its name says.** Yoast's `%%cf_key%%` and Rank Math's `%customfield(key)%` read any meta with no protected-key check and publish it in the `<title>`. Both plugins clean values as they save (tags, `%xx` octets), so a policy must judge what gets stored, not what was sent: `%%c%aaf_x%%` becomes the live variable. Run the plugin's own sanitizer on a copy rather than stripping octets yourself, because `cf` is also two hex digits. `policy_of` keys on the plugin, not one ability, because a release can add a write that takes a template.
- **`plugin-inventory.spec.ts` pins what each plugin offers once set up.** It fails when a release adds an ability: read what it does before adding the name.
- **Other plugins' data must never take the store down.** Abilities are read through `ToolRegistry::add_late_source()`, once and only when something needs a tool not already held: not before `init` (core errors) and not on every page (it runs every plugin's registration callback). A clashing name is skipped and a throwing source logged, never fatal. A malformed `required` is normalized in `AbilityTool`, and a write declaring its own `confirm` is not offered.
- **`input_schema()` keeps `properties` an array.** `ToolDispatcher::published_schema()` is the one edge that turns an empty list into `{}`; core's sanitizer throws on an object.

## The MCP protocol (state as of October 2026)
Read the spec source, not summaries: `github.com/modelcontextprotocol/modelcontextprotocol`, `docs/specification/<revision>/` and `schema/<revision>/schema.ts` at the revision's tag. Latest released revision: **2026-07-28** (the next is only `draft`).
- **Be dual-era.** 2026-07-28 is stateless: no `initialize`, every request carries `_meta` (`io.modelcontextprotocol/protocolVersion` and `/clientCapabilities` required, `/clientInfo` optional) plus the `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers, which must match the body (`-32020` HeaderMismatch, HTTP 400). But the official TypeScript SDK v2 client still opens with the 2025 `initialize` handshake **by default** (modern negotiation is opt-in), so the legacy path is what real clients use. An `initialize` request selects legacy semantics; a request with modern `_meta` is served statelessly. Never drop the legacy path without evidence the clients have moved.
- **Modern requests:** an unsupported version gets `-32022` with `data.supported` (HTTP 400). An unknown method gets HTTP **404** with `-32601`. Every result carries `resultType` (`complete` or `input_required`), and its `_meta` should carry `io.modelcontextprotocol/serverInfo`. `server/discover` is mandatory; it returns `supportedVersions`, `capabilities`, `instructions`, and caching hints.
- **Caching hints are required** on `server/discover` and the list/read results (`ttlMs` ≥ 0, `cacheScope`). Ours vary by token (scoped tool lists, instructions that name granted groups), so they are always `"private"`. The spec explicitly allows `tools/list` to vary by authorization, and asks for a deterministic order.
- **Tool annotations default to the unsafe reading:** `readOnlyHint` false, `destructiveHint` **true**, `idempotentHint` false, `openWorldHint` **true**. Always send all four. Our tools act only on the store, so `openWorldHint` is false; a bridged ability answers true, because nothing here knows what third-party code reaches.
- **Confirmation belongs in MRTR, not in an argument the model sets.** For a client that declares `elicitation` (form) in its capabilities, a gated `tools/call` returns `resultType: "input_required"` with an `elicitation/create` form, and `requestState` that is integrity-protected (HMAC) and binds the token, the tool, a digest of the arguments and a short expiry; tampered or replayed state is rejected. Clients without elicitation keep the `confirm` argument. Never put credentials in a form elicitation.
- **Transport:** an `Origin` that is present and not allowed gets HTTP 403, before authentication (`OriginPolicy`: the store's own origin, loopback origins on any port, plus the `counterhand_mcp_allowed_origins` filter; server-side clients send none). GET or DELETE on the endpoint answers 405. Ignore `Mcp-Session-Id` and `Last-Event-ID`; nothing here is session state.
- **Deprecated in 2026-07-28** (do not adopt): Roots, Sampling, Logging, the HTTP+SSE transport, and Dynamic Client Registration (CIMD replaces it, and we already use it).
- **Conformance:** `tests/e2e/specs/conformance.spec.ts` runs the pinned official suite through a local proxy that adds a token minted by the real consent flow (never an auth bypass in the plugin), for both eras. Checks that need the reference server's diagnostic tools, or capabilities we do not offer yet, are baselined per check with a reason in `tests/e2e/conformance-baseline.yml`; the runner fails when a baselined check starts passing, so delete the entry when a feature lands. `npx conformance authorization --url <store>` covers our OAuth server.

## Adding a tool
Tools are **declared, not written**. `GeneratedTool` serves the whole wc/v3 and wp/v2 surface; a new resource is a `DescriptorProvider` under `Features/WooCommerceTools/Descriptors/` plus one line in `StaticDescriptorCatalog::shipped()`.

- **Never restate a schema.** A `FieldProfile` carries *field names only* — types, enums, defaults and descriptions are read off the live route at runtime. A profile that also carried types would be a second copy of WooCommerce's schema, and copies rot. Verify names against the checked-in fixtures (`WcRouteArgsFixtureTest` fails on a name WooCommerce does not declare) and against a real store, not against memory.
- **Prune hard, but only because there is an escape hatch.** `describe_woocommerce_fields` returns any WooCommerce tool's full derived schema, and writes set `additionalProperties: true` so a revealed field can be sent straight back. It refuses integration tools, which publish all they accept, because answering would fingerprint a store's plugins. Curate to the ten or so fields that matter; do not widen a profile just because a field exists.
- **Never hardcode a capability.** Visibility comes from `RoutePermissionProbe` running WooCommerce's own `permission_callback`. If the `WordPress.WP.Capabilities` sniff fires on a new literal, something was reimplemented — `phpcs.xml.dist` must keep listing only `manage_woocommerce`.
- **Probe the collection, not the item.** `map_meta_cap()` denies an id-less item capability, so probing `/products/{id}` hides the tool from administrators too. Use `read_probe`/`write_probe` only where the collection genuinely cannot answer — and say why in a comment, because the override looks wrong without one.
- **A new group ships disabled** (`enabled_by_default()` false, no `in_chat_by_default()`) and its write axis needs its own `ApiScope` case (an integration uses `IntegrationGroup` instead, and passes `writable: false` to stay read-only). Omitting the `:write` case is how a group is kept read-only; the factory refuses to build a write with no scope to gate it.
- **Risky writes** declare `requires_confirmation` and, where the danger is in the arguments rather than the route, an `ArgumentPolicy`. Put the rule on the interface, never as a branch inside `GeneratedTool`.
- Update `ShippedSurfaceTest::SHIPPED` deliberately, by reading the catalogue — never by pasting what the failure printed.

## Integrations must survive the other plugin's update
A plugin can change on any store, on any day, without a release of ours.
- **Nothing may fatal or lie.** A route that disappears hides its tool (`RouteCatalog::has`) and the integration's row. An exception from third-party code becomes a failed call (`ToolDispatcher`). `class_exists` guards a hand-written tool.
- **`declared_arguments` is the one permitted copy of a schema, and only for a route that publishes none.** Contact Form 7 declares nothing, so there is nothing live to derive from. The live route wins on any name, so a plugin that starts declaring takes over with no edit, and an operation with declared arguments stays `additionalProperties: true`, even when gated, so a field added upstream can still be sent.
- **Copies are checked against the latest release, every day.** `tests/e2e/specs/integrations.spec.ts` runs the real plugins, unpinned, in a fresh CI store on a daily schedule (`keep-schedule-alive` stops GitHub disabling it on a quiet repo), and it asserts behaviour that a schema cannot, such as a write persisting (CF7 only saves when `context` is `save`). A new integration gets a spec there in the same change.
- **A resource on routes that exist without its plugin declares `requires_function`.** ACF adds a field to wp/v2 routes, so the route table cannot say whether it is installed. Such a tool publishes only `id` from the route plus its declared argument, closed. Only an open `FieldProfile` falls back to every argument when none of its names match; a closed one exists to keep those arguments out, so it stays closed.
- **`RestRequestGuards` changes how a plugin answers for one request carrying its forced marker.** ACF password fields stay out in both directions, because ACF returns them in plaintext, including inside a group, whose sub-fields are written one by one (`acf/pre_update_value`). `KEEP_UNSENT` sends named fields as stored, for a plugin that resets what a write omits. CF7 and ACF writes lose `unfiltered_html`, so a token cannot store script for visitors. CF7's Brevo settings survive a save, because its module otherwise resets them from an empty `$_POST`. ACF's `_acf_field_group_scope` and `_acf_field_key_map` keys were checked: they cannot reach a group not shown in REST.
- **Arguments are validated as sent, before sanitizing.** Sanitizing first turned an object sent for a string into the word `Array` and passed validation. A closed schema still drops undeclared arguments rather than refusing them.
- **Read the plugin's docs and source, and inventory it in its set-up state, before designing against it.** A fresh install can hide what a configured store exposes.
- **Germanized 4.1 declares its route args, so its tools derive like WooCommerce's, and writes stay closed.** `/products` also accepts `regular_price` and `status`, which a Germanized grant must not reach. `differential_taxation` sets the tax status to none and clearing it does not restore it, and `photovoltaic_system` zero-rates at checkout, so both are read-only. It decrypts direct-debit bank details into every order and customer response: our `_fields` lists keep them out, `MetaKeyPolicy` refuses the keys, and a test holds every order and customer tool to a field list without them.
- **Germanized's write path has traps a schema does not show.** Any product write omitting `min_age` clears it, so every tool writing through `/products` or its variations sends `KEEP_UNSENT`, `set_product_meta` included. A deposit type resets its packaging the same way. A term that does not exist answers success: a delivery time creates one named after the id, and others clear (`LegalDetailsPolicy`). Reads force `context=edit`, because `view` gives a product with no delivery time the store's default.
- **A feature supplies its own wording.** `IntegrationCopyInterface`, next to the integration; `Tokens/Domain` holds no plugin names. Integrations stay out of public discovery (`PublishedScopes::publicly_listed()`), so a store's plugins cannot be fingerprinted; consent offers the enabled ones, never pre-ticked.
- **Our own update exposes nothing new.** Integrations ship off, a token never gains a scope, and a shipped tool name or scope is a contract (`ShippedSurfaceTest`).

## Verifying against a real store
Unit tests run without WordPress, so they cannot tell you whether a field name is real, whether a route exists, or whether a probe answers true. Every bug found in the tool expansion was found this way and could not have been found any other way. The store, how to drive it, and the findings so far are in memory (`local-woocommerce-store`, `wc-schema-derivation-verified`, `wc-meta-security-findings`, `wc-risky-write-gating`). Run `wp eval-file` scripts that build the real tool set and check: every profile name is a declared route arg, every tool is available to an administrator, and a sample of each group dispatches.

## Naming
- **Full words, never abbreviations. No exceptions.** `counterhand_freemius()`, not `ctrh_fs()`; `$licence`, not `$lic`; `$counterhand_group`, not `$ctrh_group`; `counterhand_tokens`, not `ctrh_tokens`.
- This covers **everything** a name can be: PHP identifiers, template variables, hooks, filters, options, transients, database tables, constants, CSS classes and custom properties, JS globals, query vars and HTTP headers. WordPress has one global namespace, so prefixes are unavoidable — but the prefix is `counterhand_` / `COUNTERHAND_` / `counterhand-`, spelled out. A namespace claim is not a licence to abbreviate.
- The cost of a longer name is a few characters; the cost of an abbreviation is every reader afterwards having to learn it. `ctrh_ac_` took a look at the source to decode as "authorization code".

## PHP
- **PHP 8.2+**, not 8.1: `final readonly class` is an 8.2 feature (readonly *properties* are 8.1) and 86 files use it. `composer.json`, `phpcs.xml.dist` (`testVersion 8.2-`) and `readme.txt` all agree; keep them that way, because WordPress.org enforces the readme value and a mismatch blocks installs on stores that would otherwise be fine.
- Use: `final readonly` classes, constructor promotion, backed enums, `match`, named arguments, `never` return type where applicable.
- **Avoid `else` — happy path last.** Guard clauses return/throw/redirect early; the main flow reads top-to-bottom unindented. (`if/else` in templates for markup branching is fine.)
- Zero runtime Composer dependencies. Never vendor a library that could collide with core or other plugins (`src/Autoloader.php` explains why). WordPress-bundled libraries (e.g. the WP 7.0 AI Client) are used behind a capability check and a stub file for PHPStan.
- WPCS via `phpcs.xml.dist` (WordPress-Extra, Yoda conditions, i18n text domain `counterhand-mcp-for-woocommerce`). PHPStan level 6 with stubs in `tests/phpstan-*.php`.

## Comments
- Only when needed, and short — one line unless the *why* genuinely needs more.
- Comments explain why, never what. No restating the code, no section banners in PHP.
- **Never comment the obvious.** If the line already says it, the comment is noise — a `// stdClass so it encodes as {}` beside `new \stdClass()` tells the reader nothing they cannot see. Write only what the code cannot say: the consequence, the constraint, the thing that breaks otherwise.
- **Say it once, where the decision lives.** The same reason repeated at every call site and test that touches it is worse than no comment — it goes stale in five places instead of one.

## UI
- Design tokens from `assets/shared/tokens.css` (mapped to `--wpds-*` with fallbacks). No raw hex in admin/OAuth CSS, never hardcode WooCommerce purple `#7f54b3`.
- Admin screens use the whole canvas, as core and WooCommerce do: card lists reflow into as many columns as fit (`repeat(auto-fit, minmax(30rem, 1fr))`), only running text carries a measure (`--counterhand-prose`, 68ch). White cards, one idea per card.
- No JS build step; hand-written ES5-flavoured IIFEs. No remote assets (WordPress.org rule).
- Escape-then-format for any model output rendered as HTML (`chat.js formatAnswer`).

## Verification
- `composer run lint` (phpcs), `composer run analyse` (phpstan, needs `--memory-limit=1G`), `composer run test` (phpunit) — all green before claiming done.
- `npm run e2e` (Playwright, see `tests/e2e/README.md`) for anything a user can see or an MCP client can call. It runs against the plugin's own disposable **devbox** store in `tests/e2e/store` (`npm run e2e:store:start`), never Docker or wp-env, and never the marketing site's store. A new user-facing flow gets a spec in the same change.
- npm is test tooling only: `package.json`, the lockfile and `playwright.config.ts` are in `.distignore`, and the plugin never loads anything from `node_modules`. The no-build-step rule for shipped JS still holds.
